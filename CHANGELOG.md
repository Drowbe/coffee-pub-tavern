# Changelog

All notable changes to Coffee Pub Tavern. Format follows Keep a Changelog, and versions follow SemVer.

## [Unreleased]

### Added
- What dropping one module's item on another does is now one shared decision, `tavern.refs.dropMenu`, instead of each module's own (an audit found four: Calendar and Planner built a menu of choices, copied between them; To-do and Polls only linked; Research always started a note; Maps looked one action up by name; Places and Assistant took no drops at all). A target says what is under the pointer (the drop context: the card, its own item there, the day, the time, the map position) and what it would offer of its own; the SDK adds what the dropped item's own module can do with it there -- set this task's due date to this day, link this task to this event, put this place at this spot on the map -- and shows one menu; one offer runs at once with nothing asked. A drop is about the item and what is here: a third module making something new of the item is not offered (the first version did, and a research note dropped on a plan day asked about a calendar event, a task and the assistant instead of just landing on the day). An action can say what the item it takes must have (`needs: ["place"]` on `actions.provides`), and the menu wears each offer's module icon, in the same look as `tavern.menu.show`. A drag can carry a card instead of a pointer, for a module with nothing stored: an answer the assistant wrote drags onto a plan, the calendar, a task or research as itself. Calendar's `createEvent` links the item it was made from; To-do's leftover browser-drag handlers are gone. Planner's typed-card placement (`acceptSuggestion`) is `fromSuggestion`, shared with its drop. All eight modules: Assistant 0.1.9, Calendar 1.17.3, Maps 0.7.5, Places 0.8.6, Polls 1.12.5, Research 0.2.4, To-do 1.11.3, Planner 0.7.17. The fill rules are `tools/check-drop.mjs`, part of `npm run check`; the design is `documentation/plans/plan-drop.md`, the contract "Dragging" in `api-module-sdk.md`. The chat as a drop target is left (host-side).
- The module window framework: a titlebar, an optional toolbar under it, the content, and an optional action bar -- the same four zones and the same overflow rule everywhere a module can be shown (docked, floating, its own window, its own page), documented in `documentation/architecture/architecture-module-window.md`. `tavern.toolbar.set([...])` is a new optional row under the titlebar for text, a tab switch, a progress bar, a slider or a button, reusing the same reuse-across-dock/float plumbing the frame and action bar already had, so a module's toolbar survives a dock<->float switch too; it is deliberately not a second row of titlebar icons, so a tab switch is text, not more icon buttons. `tavern.ui.viewSwitch({ id, options, value, onChange })` is the toolbar's first reusable tool -- a labelled view or filter switch that owns its own diffing and event wiring, so a module calls `.set(value, options?)` on every render instead of hand-rolling it. `header.set`, `bar.set` and `toolbar.set` now collapse anything past five items (or one marked `overflow: true`, always tucked away) into a host-drawn "..." instead of silently dropping it -- the host's own analogue of `tavern.menu.show`, for its own chrome rather than a module's frame.
- `tavern.menu.show({ id, items, at, anchor })`, a shared, reusable action menu drawn inside a module's own frame, replacing near-duplicate "..." menus each with its own positioning math and Escape/outside-click handling. Gained `iconColor` (an item's own icon in a fixed color, for a set of kinds already told apart by color elsewhere, e.g. Planner's marker types) and `href` (a real link, not a click handler faking navigation, so hovering, copying and opening in a new tab still work). Polls (1.12.4), Places (0.8.5), Research (0.2.3) and Planner's (0.7.15) gap-add menu are now on it; a module's own item menu with real form fields (a day picker, a type picker) stays native, since the shared menu only draws a flat list of actions.
- Polls (1.12.4), Calendar (1.17.2), To-do (1.11.2) and Planner (0.7.15)'s Open/Closed/All, Month/Week/Month+list/List, Open/Done/All and Days/Decisions/Bookings/Money switches moved off titlebar icons and onto the toolbar's `tavern.ui.viewSwitch`, each now text tabs instead of icons repeating the module's own name. Planner's two other titlebar actions (Hide/show empty days, Edit trip) are unaffected -- they are actions, not a view switch.
- A `tabs` toolbar item's options can now carry an icon, a label, or both (`iconOnly` keeps the icon and drops the visible label), the same shape `bar.set`/`header.set` items already had -- for a switch where the icon itself is meaningful, not decorative. Places (0.8.5) and Research (0.2.3)'s own Mine/This room/Everyone switch, previously a bespoke pill row built into each module's own page, moved onto `tavern.ui.viewSwitch` with it. `.mod-toolbar` scrolls horizontally instead of clipping when a row does not fit a narrow pane.

Verified live against a running server: the toolbar's tabs (text-only and icon+label), text, progress and slider render and dispatch events correctly (via a temporarily-instrumented Polls build, reverted after), Places' menu opens, arms and deletes a real place and its "Open in my maps app" is a real link, Planner's gap-add menu adds a marker with each type's own icon color intact, and Places' Mine/This room/Everyone switch (all three options, an icon and a label each) switches correctly down to a 280px-wide pane.

### Changed
- Rooms are **spaces** in everything a person reads: the navigation, the pages, the buttons, the tooltips and the modules' own views ("This space" beside "Mine"). The code, the routes (`/rooms/:id`), the API fields and the stored data keep `room`, so nothing anyone has stored or linked changes; the documentation's prose follows in its own pass (see TODO.md). Done as one sweep over the pages' text and attributes and the prose in their strings, with the code left alone, then checked for anything code-like caught in it.
- The header's rows have their own colours, as theme tokens: the primary nav's middle zone is the header colour, its left and right zones a shade darker (`--nav-primary-edge-bg`), and the secondary nav (the space's bar) its own (`--nav-secondary-bg`), between the header and the page. All three derive from `--header-bg` until a theme sets them (`design-theme.md`); the theme editor does not offer them yet.
- The crumb is gone at the table: the secondary nav names the space, so the primary nav's "> Lobby" said it twice. The aside's Rejoin call button, which lived in the crumb, is in the secondary nav's right zone with the other space actions. On every other page the crumb still says where you are (Server Settings, a profile, a module's page), since those have no second row.
- The header is two rows in three zones each, and every control now has a zone by what it is about (the system or the space) and what it does (navigation, action, information), not by where it fit. The primary nav (every page): left, the logo and where you are; middle, centred on the row whatever the other zones hold, the core navigation (Rooms, each module's own page, shown with their names now rather than as bare icons); right, the system's actions and information (your profile, Manage, Install, the time on the server's clock, Sign out). The secondary nav (the room bar, at the table): left, the room's name and the module selector; middle, the space's own information and navigation (empty so far); right, the space's actions (the stage-level snap, Full screen, Pop out, Pull participants back -- moved here from the primary row, since it is the room's action -- and Leave). On a phone the primary row keeps the logo, the crumb and a menu, with the middle zone's links moved into the menu, and the secondary row is the tab bar as before. Documented in `architecture-navigation.md`; what each zone grows to hold, and modules registering tools into the bars (after the author's Blacksmith menubar), are in `documentation/plans/plan-nav.md`. Verified live: both rows measure with the middle zone at the row's centre and the right zone flush right, at the table and on the room list; the phone menu takes the core links.

### Added
- The stage-level snap: a switch in the room bar (beside Full screen) that puts every pane that can float onto the grid -- docked ones are floated first, their docked mode remembered, and any pane opened later comes up floating and snapped; off, the ones that were docked dock again -- and, while it is on, a slider for the grid's size (the grid shows while it moves, and every snapped pane refits). The grid is about half the size it was (a 130px pitch, adjustable from 60 to 320), and a pane never takes fewer cells than its smallest size needs, so a fine grid still gives a usable pane. Both are remembered with the room's layout. Verified live with the chat pane: the stage switch snapping it and setting its own switch, the slider previewing the grid and refitting the pane, releasing hiding the grid, the stage switch off, and the pane's own switch still working alone.
- Language, time and money: a new section on Manage > Settings' Server tab. **Clock** (12-hour, the default, or 24-hour) is how every time is shown across the server and every module; **Currency** is the one amounts are shown in unless a trip names its own; **Language** is the interface language (English only, until translations arrive). The SDK carries them to modules (`tavern.locale()`, `tavern.util.time`, `tavern.util.hour12`, `tavern.util.money`), and Planner (0.7.24; every time on a card, a row, a day's summary, the trip markers and the Trips widget, and money through the server's currency when the trip has none), Calendar (1.17.4, and its widget), Polls (1.12.7, and its widget) and To-do (1.11.5) follow them; before, Planner always showed 24-hour times and the others took the browser's choice. Showing a trip's own currency with a conversion beside it is left until a source of exchange rates is chosen (see TODO.md).
- Planner (0.7.22): a marker with no time marks the whole day -- "Travel day", "Free day" (two new default marker types, beside the timed ones) -- drawn as a tag in the day's header in its marker's colour rather than as a row among the day's items; clicking the tag opens its menu (edit, move, change type, remove). The day's "..." gained a "Mark the day" group that adds one at once, ahead of the timed blocks, which now read "Add free time at a time". A card folds what its face has no place for under a "More" line: the note, who is on it, the booking reference, the terminal, the platform, the room, the cost and who paid, only what the item has and the face did not show; a card someone opened stays open through redraws. The editor's placement field is **When** (it was Where for a day), and a length is any whole number of minutes (it was steps of five; minutes matter in travel).
- Research (0.2.6): cards pack like masonry -- each takes the rows its own height needs, so a short card beside a tall one leaves no hole under it, and the columns follow the pane's width -- and a **Cards / List** switch beside Mine / This room, the list being one line per item; remembered per person. `tavern.ui.viewSwitch` learned to share the toolbar between several switches (in the order they were made, a separator between), so a module's second switch does not draw over its first. Not run live here (Research needs the server's AI service on): checked as code, the switch composition in a node check of the SDK.
- A floating pane can snap to a grid. Floating was only ever free (anywhere, any size); a floating pane's titlebar now has a **Snap to a grid** toggle that makes it sit in the cells of a grid laid over the stage (cells of about 260 x 200, as many as the stage fits, a 16px gutter): dragging moves it a cell at a time, resizing grows it a cell at a time, the grid shows while it moves, and what is remembered is its cells, so a window resize re-tiles it rather than just keeping it on screen. Off, it floats freely as before; turning it on settles the pane into the nearest cells at once. Docked and window are untouched -- snap is a way of floating, not a replacement for docking -- and a pane keeps its DOM through every snap, as through a free drag. The chat and every module pane have it; documented in `architecture-room-layout.md` ("Free or snapped"). Verified live on the chat pane with the call unavailable: toggling on, a snapped drag and resize (with the grid shown), free again, snapped again, and a viewport change re-tiling it.
- Planner (0.7.21): the plan line. Anything can now sit *between* days as well as on one -- an idea near the first day, a few more near the tenth, a poll between two days, a research card near day 3 -- and the organizing rule is date, then time, then where a person placed it. Every item is in one of two places, and the model enforces it: on a day (`date`, `time`, `order`) or on the line at a joint (`after`, the day the joint follows, `''` for the head before the first day; then `order`). Nothing stored changed shape: the old Ideas column is simply the head of the line, and a between-days marker was already placed that way. So Ideas is gone as a column and the items with no day yet are drawn on the line before Day 1, the same way a marker between days always was; a card on the line is the card it would be in a day, with no time. Every joint takes anything: its + offers the same kinds the day's "..." does (plus the between-days marker types, added at once), the editor's Day field became **Where** (the days and the joints in line order, "Before the first day", "Between Oct 1 and Oct 2", "After the last day"; a marker sees only the joints), **Move to** in an item's menu lists the same, and **Back to ideas** became **Back to the line** (off its day, to the joint before it). Dropping: while anything is dragged over the plan -- one of its own items by its body, or another module's item or card -- every joint opens into a drop zone, as it did only for a marker before; a plan's own item dropped on a joint moves there, among the items already at it; another module's item dropped on one is offered "Put it here, between Oct 1 and Oct 2" through the shared drop menu. Earlier and Later on the line swap with a neighbour at the joint and hop to the next joint at the ends. A hidden day's joint still draws its items after the hidden-days badge, so nothing disappears with the day. The design and the author's mental model (what do I know, what are my options, what are my decisions) are in `documentation/plans/plan-travel.md`; `tools/check-travel.mjs` covers the placement rule. Verified live: Move to a joint and back, Back to the line, the joint's + adding a note at that joint through the editor, a To-do task dropped on a joint, a card dropped on the head of the line, a plan item dragged by its body onto a day and back onto the line before a marker.
- The SDK delivers a module's own dragged item to its own `tavern.refs.dropTarget` when it is dropped on the module itself (`over`, `leave`, `drop`, with its own pointer as `ref`), so moving an item within a module is the same code path as taking one from another; the host only ever handed a drag to the *other* modules, which had left Planner's own between-days marker drag (built on `dropTarget`) unreachable by the pointer. Documented in `api-module-sdk.md` ("Dragging"), with the one thing it implies: `leave` comes just before `drop`, so a drop zone that opens while a drag is over you must not close on `leave` until a tick later, or the drop is hit-tested against the wrong layout (found live, when a drop on a day landed on the joint below it).
- Planner (0.7.19): a "..." on every day (and on Ideas) listing everything that can be added there -- each kind the editor's tiles offer (a flight, a train, a ferry, a bus, a rental car; a stay; a restaurant, a café, a bar, a sight, a museum, a tour, a show; a note) and the time blocks -- each opening the editor on that day with the kind chosen. Typing to add was the only way in before; it stays the fast path, this is the plain one.

### Fixed
- Map region cutting: after a successful cut, Check size stayed disabled for the rest of the page's life -- invisible cutting one region per page load, but every second cut in the same session (exactly the basic-then-detailed pattern above) could silently not be checked or cut at all.
- A region cut (map region download) failed on a real deployment with `EXDEV: cross-device link not permitted`: the background job wrote its temp file to the system's own `/tmp`, a different filesystem from `DATA_DIR` in a container with a separate mounted volume, so the final move into place could never succeed there (a local dev setup happens to keep both on one filesystem, which is why this passed local live testing before). The temp file now lives inside `DATA_DIR` itself (its own `tmp/region-cut/` folder, cleaned up the same way as before), so the move is always on one filesystem. Verified with a real cut against the real Protomaps daily build. `tools/check-region-cut.mjs` gained an assertion that the temp path stays under `DATA_DIR`.
- A setting's own `help` text (module.json) was silently cut off at 200 characters, mid-sentence, with nothing to say so happened -- a choice option's own help already had ten times the room (600, with line breaks kept). Maps' `worldSource` setting was the one that surfaced it (its help ends with a URL, past the 200-character mark). Now 600, keeping line breaks, the same treatment a choice option's help already had. New `tools/check-modules.mjs`.
- Map region cutting's default Maximum zoom was 10, which never shows individual streets -- a poor default for a planning app, and the field carried no explanation of what it actually controlled. Now defaults to 14 (streets and buildings visible) and explains itself: what the number trades off (detail against file size, not how far the cut reaches), roughly what 10, 14 and 15 each look like, and that Check size shows the real cost for whatever is chosen before anything downloads.

### Added
- Multiple typed cards per reply (Assistant 0.1.5, Planner 0.7.9).
